# AI Usage & Development Report

This document records how I used AI during the development of this project. I used it mainly for discussing design decisions, generating implementation suggestions, finding edge cases, and debugging. I reviewed and tested the generated code before accepting changes.

---

## 1. Which AI Tool(s) You Used
- **Antigravity AI** — agentic development environment.

---

## 2. The Prompts Given

During development, I interacted with the AI across several stages:

1. **Requirements & Scope**:
   - Asked the AI to create a `REQUIREMENTS.md` based on the assignment brief, separating functional requirements, non-functional requirements, assumptions, constraints, and out-of-scope items without adding unnecessary complexity.

2. **Implementation Plan**:
   - Asked for a practical milestone-based implementation plan where each milestone is independently testable, starting with the core recommendation logic first.

3. **Architecture & Service Layer**:
   - Asked to review the requirements and propose a simple Django architecture where business logic is separated from the HTTP/API layer so it can be tested independently.

4. **Data Model Design**:
   - Asked to design minimal Django models for `Product`, `Box`, `Order`, and `OrderItem`, explaining relationships, constraints, and validation before writing code.

5. **Algorithmic Validation (Volume vs. Dimensions)**:
   - Raised my initial thought about comparing total product volume with box volume and asked why volume-only comparisons can fail and what edge cases exist.

6. **Dimension Rotation**:
   - Asked how to cleanly handle 3D rotation so a product fits if any orientation of its dimensions fits within a box.

7. **Stress Testing**:
   - Asked the AI to help create adversarial test cases to try to break the recommendation logic with rotation traps, quantity overflows, weight limits, multiple boxes, and boundary dimensions.

8. **CI/CD & Local Setup**:
   - Asked for a GitHub Actions workflow configuration and clear instructions for running and testing the project locally.

---

## 3. What Output Was Accepted

1. **Layered Architecture (`models.py` → `services.py` → `views.py`)**:
   - Kept views thin and isolated the recommendation logic inside `services.py` without any HTTP dependencies.

2. **Dimension-Sorted Fitting Logic**:
   - Sorted item and box dimensions in ascending order (`[min, mid, max]`) and compared them element-wise to handle all orientations for rectangular cuboid fit checks without explicitly generating all six permutations.

3. **Data Models with `DecimalField`**:
   - Used `DecimalField` so dimensional and weight values are represented with decimal precision suitable for boundary comparisons.

4. **Idempotent Seed Data Command**:
   - Accepted the `python manage.py seed_data` command using `get_or_create` to populate initial product and box catalogs.

5. **Automated Test Cases**:
   - Accepted unit, view, integration, and stress test suites to ensure broad test coverage.

---

## 4. What Output Was Rejected or Modified

1. **Simplified Packing Approach**:
   - AI suggestions were reviewed against the actual requirements. I chose a deterministic single-axis stacking heuristic instead of attempting a general 3D bin-packing solution because the assignment is small and the exact optimization problem is significantly more complex. I documented this as a limitation rather than presenting the heuristic as an optimal packing algorithm.

2. **Avoided Heavy Dependencies (e.g., Django REST Framework)**:
   - Decided against adding DRF for a single recommendation endpoint. Native `JsonResponse` and standard Django views kept the project lightweight and dependency-free.

3. **Rejected Volume-Only Checks**:
   - Explicitly rejected simple volume aggregation because long/narrow items (e.g., rods) or tall stacks can fit volumetric capacity while physically protruding out of a box.

4. **Avoided Unnecessary Abstractions**:
   - Kept the code simple by avoiding extra repository patterns, DTO classes, or custom signals that would add unnecessary boilerplate for this scale.

---

## 5. Mistakes the AI Made & How They Were Corrected

1. **Django Version Incompatibility with Python 3.9**:
   - *Mistake*: The initial `requirements.txt` generated by the AI specified `Django==5.1`, which requires Python 3.10+. My local environment was running Python 3.9.2, causing installation errors.
   - *Correction*: I identified the version mismatch and downgraded the dependency to `Django==4.2` (LTS), which fully supports Python 3.9.

2. **Incorrect Test Fixture Math for Stacking**:
   - *Mistake*: In `test_services.py` (`test_multiple_products_with_quantity`), the initial test assertion assumed 3 stacked items (sorted dims `[3, 5, 10]`, stacked dimension `10 * 3 = 30 cm`) would fit inside a box with dimensions `20×15×10 cm` (`max dim = 20 cm`).
   - *Correction*: The test failed on run. I checked the math, found that 30 cm cannot fit in 20 cm, and adjusted the test fixture box dimensions to `30×15×10 cm` to match the actual stacking calculation.

## 6. How the Final Code Was Verified

I verified the code through multiple testing layers:

1. **Service Unit Tests (`shipping/tests/test_services.py`)**:
   - 13 tests checking single-item fit, rotation handling, cheapest box selection, mixed products, empty lists, and no-fit scenarios.

2. **API & View Tests (`shipping/tests/test_views.py`)**:
   - 13 tests checking HTTP status codes (200, 400, 405), response JSON structure, input validation (missing keys, invalid IDs, negative quantities), and the frontend index view.

3. **Integration Tests (`shipping/tests/test_integration.py`)**:
   - 7 tests verifying database record creation for `Order` and `OrderItem` and end-to-end API flows.

4. **Stress & Adversarial Tests (`shipping/tests/test_stress.py`)**:
   - 18 tests covering 0.01 boundary decimals, extreme aspect ratios, high quantity overflows, equal-cost ties, and zero-cost sample boxes.

5. **Local Manual Testing**:
   - Tested the live web UI at `http://localhost:8000/` by building orders with multiple items and verifying the calculated box against manual calculations.

6. **Total Automated Tests**:
   - **51 tests total**, all passing in `0.087s` via `python manage.py test`.
